# Synthetic CRM: read first, review before action

A **freshly authored demonstration**, created on 2026-10-21. It shows how an MCP
client can ask bounded questions of CRM-shaped data without receiving arbitrary
SQL, filesystem access, free-text notes, contact details, or mutation tools.

**All 12 records are invented.** No employer, client, personal, or production CRM
data was used. This is not a HubSpot integration, affiliation, endorsement, or
case study of prior marketing performance. The fixture's 2026-10-15 snapshot date
is fictional and fixed, not the server's current date.

## What you can inspect right now

- [Actual deterministic tool output](DEMO_OUTPUT.txt), generated by `demo.py`.
- [Actual MCP stdio smoke-test output](SMOKE_OUTPUT.json), generated by an SDK
  client talking to a separate server process, not mocked tool calls.
- [All invented records](fixtures.py) and [the query/field allowlist](core.py).

- [Verification results and known baseline failures](VERIFICATION.md).

No account, API key, LLM subscription, or CRM connection is needed to inspect the
files. Running the MCP transport requires the official Python MCP SDK.

## Why this is useful

A marketing or advisory team might ask: "How many records are at each stage?"
and "Which qualified records look stale enough for a human to review?" This
small example demonstrates that data-access boundary, not autonomous outreach.
Webinar, newsletter, and event campaigns are invented categories.

The default queries produce:

- 12 records: 2 leads, 3 MQLs, 3 SQLs, 2 opportunities, 1 customer, 1 lost.
- 2 records screened out of follow-up consideration by the fixture flags.
- 4 human-review candidates with 25, 21, 16, and 14 days since activity.

MQL means marketing-qualified lead; SQL means sales-qualified lead. The stage
summary is a **snapshot inventory**, not a historical funnel conversion rate.
No time savings, revenue lift, response-rate improvement, or ROI is measured.

## Run from the repository root

Python 3.10+ is required. The dependency-free query demonstration works directly:

```bash
python -m examples.crm_readonly_mcp.demo
```

To run an actual MCP client/server round trip:

```bash
python -m venv .venv
# Activate your environment, then:
python -m pip install -r examples/crm_readonly_mcp/requirements.txt
python -m examples.crm_readonly_mcp.smoke_test
```

To serve an MCP client over stdio:

```bash
python -m examples.crm_readonly_mcp.server
```

This server waits for protocol messages on stdin; a quiet terminal is expected.
Configure a client to use the virtual environment's Python executable, arguments
`["-m", "examples.crm_readonly_mcp.server"]`, and this repository as its working
directory. If the client has no working-directory option, set `PYTHONPATH` to the
absolute repository root in that client configuration. No API keys are needed.
Do not use this demo's server as a public HTTP service.

The transport uses the [official MCP Python SDK 1.x](https://github.com/modelcontextprotocol/python-sdk/tree/v1.29.0),
pinned for the example. It does not alter the approvals project's dependencies.
These examples are source-tree examples, not files installed into the
`mcp-approvals` wheel or its existing container.

## Tools and example arguments

| Tool | Accepted arguments | Result |
|---|---|---|
| `crm_data_contract` | `{}` | Data provenance, allowed fields, limitations |
| `crm_funnel_summary` | `{"campaign": "webinar"}` | Current-stage counts for one campaign or all |
| `crm_review_candidates` | `{"campaign": "all", "min_idle_days": 14, "limit": 5}` | Bounded human-review shortlist |

Campaign is exactly `all`, `webinar`, `newsletter`, or `event`. Idle days must be
an integer from 1 through 90; limit must be an integer from 1 through 20. Booleans,
floats, numeric strings, unknown arguments, and unknown tools are rejected. Both
the tool schemas and server-side validation define the boundary; annotations
such as `readOnlyHint` describe the tools but are not security enforcement.

Candidate screening requires the synthetic `opted_in` flag, no
`do_not_contact` flag, an MQL/SQL/opportunity stage, and the requested minimum idle
period. Those flags are illustrative business rules, not proof of legally valid
consent. Ordering is descending idle days, then ascending synthetic record ID.
An exact idle-day threshold qualifies. `matched_count`, `returned_count`, and
`truncated` make output limits explicit.

The only record-level fields returned are `record_id`, `campaign`, `stage`,
`days_since_activity`, and a fixed `review_reason`. Internal notes and raw
screening flags stay out of record-level responses. Names, email addresses, phone
numbers, and other contact details do not exist in the fixture. Aggregated stage
counts intentionally include screened-out records; review candidates do not.

## Boundaries that are implemented

- Fixed, immutable records in source code; no configurable path or data import.
- Three named read-only tools; no SQL, arbitrary query, export, send, update,
  delete, or approval operation.
- Fixed output field projection. A test inserts adversarial instructions into an
  internal note and verifies the note never reaches the tool response. This is
  not a claim of general prompt-injection immunity.
- Explicit input validation, short error messages that do not echo attacker
  input, a 20-row maximum, and deterministic behavior across repeated calls.
- No network requests, credentials, CRM SDK, or third-party account sign-in in
  the demonstration code. Installing dependencies requires registry access.
- Stdout carries MCP protocol only when serving; the demo and smoke commands are
  separate, human-readable entry points.

## What this does not implement

This is an instructional local stdio server, not a production security boundary.
It has no authentication, authorization, tenant isolation, external data adapter,
consent verification, retention policy, durable audit logging, or request-size/
rate limiting. The process is not sandboxed by this code. Source readers can see
all invented fixture fields. Do not replace fixtures with private data and assume
these limitations disappear.

It does not call or enforce the repository's approval gate. A review candidate is
**not authorization to contact anyone**. A real write path would need separate
explicit authorization and enforcement at the system that performs the action,
with authenticated identities, least-privilege scopes, and a reviewable audit
trail. The existing [approvals server's limitations](../../README.md#scope-and-limitations)
remain unchanged. A production CRM adapter would be a separate project change,
not a configuration switch hidden in this example.

## Verify and reproduce

From the repository root, install development tools and the pinned example SDK:

```bash
python -m pip install -e ".[dev]"
python -m pip install -r examples/crm_readonly_mcp/requirements.txt
python -m pytest tests/test_crm_readonly_mcp.py
python -m ruff check .
python -m mypy
python -m mypy --strict -p examples.crm_readonly_mcp
python -m examples.crm_readonly_mcp.demo > /tmp/crm-demo-output.txt
diff -u examples/crm_readonly_mcp/DEMO_OUTPUT.txt /tmp/crm-demo-output.txt
python -m examples.crm_readonly_mcp.smoke_test
```

The existing CI discovers the new tests in `tests/`, including the real stdio
round trip. A dedicated `CRM read-only example` workflow also checks this example
on Python 3.10, 3.11, and 3.12 independently of the approvals-core tests. See [VERIFICATION.md](VERIFICATION.md) for what passed and the two
pre-existing repository tests that fail under the actual current clock.
